# Data Model: Customer Authentication

## CustomerAccount

Represents an identity created through customer self-registration. It is separate from the operational `Customer` profile and `AdminUser`.

**Fields**
- `id`: generated unique identifier
- `name`: required customer name as entered
- `username`: generated, unique customer sign-in name
- `address`: required structured postal address using the existing `Address` shape (`streetNumber`, `postalCode`, `city`, `province`); this address belongs to the account and does not link the account to an operational `Customer`
- `email`: normalized, unique customer contact address
- `phoneNumber`: required customer contact phone number stored in international E.164 format, including country code
- `passwordHash`: algorithm-prefixed one-way encoded password produced by Spring Security `PasswordEncoder` (using an adaptive encoder and a unique salt)
- `role`: server-assigned customer role (`CUSTOMER`); not accepted from registration input
- `status`: account state; self-registration creates an `ACTIVE` account
- `createdAt`: account creation timestamp
- `lastLoginAt`: timestamp of most recent successful sign-in, nullable until first login

**Validation rules**
- Name, address, email, phone number, and password are required. Username is generated by the service; it is not supplied by the registration client.
- Generate the username base by converting the name to lowercase and removing all whitespace while preserving other characters. Append a sequence for that base, starting at `001`, incrementing for each duplicate name base, and padding to at least three digits (`1000` and above are not truncated).
- Enforce username and normalized email uniqueness with database constraints. Username allocation must handle concurrent registrations so no duplicate username is returned or persisted.
- Trim and normalize email consistently before lookup and persistence.
- Email must satisfy a syntactic email validation rule and application field-length limits.
- Phone number must include a country code, pass E.164 validation, and be stored in E.164 format.
- Address fields use the existing structured address conventions. Do not create or link an operational bank `Customer` or `Account` merely from customer-auth registration.
- Passwords must be at least 8 characters; allow passwords of at least 64 characters and do not impose arbitrary composition rules.
- Passwords are never stored in plaintext or returned by an API. Use Spring Security `DelegatingPasswordEncoder` with an adaptive encoder; tune its work factor to target hardware and retain the algorithm identifier so future encoding upgrades are possible.
- Registration assigns `CUSTOMER` and `ACTIVE` server-side. The public request cannot set role, status, admin flags, or operational customer/account associations.
- Sign-in queries only this entity type. An admin record is not a customer credential.
- Repeated failed customer sign-in attempts are temporarily rate-limited; they do not permanently disable an account. Return a generic response and a retry delay without revealing account existence.

## Customer Authentication Session

Represents an authenticated browser customer session using Spring Security's server-side `SecurityContext` persisted in the servlet HTTP session. It is not stored in the admin `sessions` table.

**Session state**
- principal: authenticated `CustomerAccount` identity
- authority: server-derived `ROLE_CUSTOMER`
- `createdAt` / last activity: managed by the server session
- `expiresAt`: server-enforced idle expiry (15 minutes, matching the existing admin session duration)
- CSRF token: Spring Security-managed token required for state-changing customer requests

**Validation rules**
- Spring Security's session-fixation protection rotates the session identifier upon successful authentication.
- A customer-only backend endpoint must validate an active session and the customer principal; client-side route guards are navigation UX, not authorization.
- Logout invalidates the server session and expires the cookie.
- Customer logout and session validation do not revoke or mutate the admin session.
- Cookie is `HttpOnly`, has an appropriate `SameSite` policy, and is `Secure` in HTTPS deployments.

## AdminAccount

The existing `AdminUser` remains the identity for internal staff. Its roles, login route, session association, and admin operations are not changed by this feature. Customer registration does not create, update, or link an `AdminUser`.

## Relationships

- A `CustomerAccount` may have zero or more active browser sessions; each session references only the authenticated customer account and is governed by the server's session policy.
- A `CustomerAccount` owns its required postal address; this address is not a relationship to the bank's operational `Customer` profile.
- `CustomerAccount` has no relationship to existing operational `Customer` or `Account` records in this release.
- Admin identities remain associated with the existing admin `Role` and `Session` model.

## State Model

### Customer account

- `ACTIVE` → may sign in.
- `DISABLED` → sign-in denied.
- Self-registration creates only `ACTIVE` customer accounts; administrative account-state management is out of scope.

### Customer session

- Anonymous → authenticated after valid customer credentials.
- Authenticated → invalidated on logout or idle expiry.
- A customer session never grants access to admin-only resources.
